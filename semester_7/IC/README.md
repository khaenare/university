# Інформаційна система моніторингу роботи СУБД

Система безперервно генерує навантаження на БД PostgreSQL (навчальний
інтернет-магазин), збирає метрики, логи і трейси її роботи та відображає їх у
Grafana. Доступ до системи мають лише авторизовані користувачі.

## Архітектура

```
Доступ користувача:

  Браузер ──:8080──► nginx (шлюз) ──перевірка сесії──► auth (Flask + SQLite)
                         │
                         ├──► Grafana ──► Prometheus, Loki, Tempo
                         └──► Prometheus UI

Потоки даних моніторингу:

  generator (Python) ──SQL──► PostgreSQL ◄── postgres-exporter
     │  │  │
     │  │  └─ метрики /metrics ──► Prometheus ◄── postgres-exporter, auth
     │  └──── трейси (OTLP) ─────► Tempo
     └─────── логи (stdout) ─────► Alloy ──► Loki      (логи всіх контейнерів)
                                     ▲
                       docker-proxy ─┘  (Docker API лише на читання)
```

Відкритий лише порт **8080** (шлюз) і лише на цьому комп'ютері (`127.0.0.1`):
система працює по HTTP без шифрування, тому з локальної мережі вона недоступна.
Grafana, Prometheus, Loki, Tempo і PostgreSQL доступні тільки всередині мережі Docker.

## Склад сервісів

| Сервіс | Призначення |
|--------|-------------|
| `postgres` | СУБД PostgreSQL 16, БД `shop` (таблиці `customers`, `products`, `orders`) |
| `postgres-exporter` | Віддає метрики PostgreSQL (з'єднання, транзакції, рядки, розмір БД, кеш); роль `exporter` лише читає статистику |
| `generator` | Імітує роботу застосунку: реєстрація клієнтів, замовлення, зміна статусів, звіти, очищення; частина запитів навмисно повільні або помилкові. Роль `shop_app` — лише робота з даними таблиць |
| `auth` | Сервер авторизації: сторінка входу, перевірка сесій для шлюзу, CLI для керування користувачами |
| `gateway` | nginx: усі запити до Grafana/Prometheus спершу перевіряються в `auth` |
| `prometheus` | Збір і зберігання метрик |
| `loki` + `alloy` | Зберігання і збір логів |
| `docker-proxy` | Доступ Alloy до Docker API лише на читання (список контейнерів і їхні логи) |
| `tempo` | Зберігання трейсів |
| `grafana` | Візуалізація; вхід через auth proxy (логін і роль приходять від шлюзу) |

## Запуск

Потрібен Docker Desktop (або Docker Engine + Compose v2).

Спершу створіть `.env` із шаблону і заповніть у ньому всі паролі (файл `.env`
не потрапляє в git). З порожнім паролем система не запуститься.

```bash
cp .env.example .env
```

Згенерувати надійний пароль можна так:

```bash
openssl rand -base64 18
```

Паролі PostgreSQL (`POSTGRES_PASSWORD`, `APP_DB_PASSWORD`, `EXPORTER_PASSWORD`)
застосовуються лише при першому створенні бази. Якщо змінити їх у `.env` пізніше,
генератор напише в лог `Невірний логін або пароль до БД`. Щоб змінити пароль
існуючої бази, виконайте `ALTER ROLE <роль> WITH PASSWORD '...'` у `psql` і
оновіть `.env`.

```bash
docker compose up -d --build
```

Мережа проєкту має фіксовану підмережу `172.29.42.0/24`. Якщо Docker повідомить
про конфлікт (наприклад, з VPN), змініть її в [docker-compose.yml](docker-compose.yml)
разом з адресою шлюзу та `GF_AUTH_PROXY_WHITELIST`.

Через ~20 секунд відкрийте **http://localhost:8080** і увійдіть з логіном і
паролем адміністратора з файлу [.env](.env) (`ADMIN_USERNAME` / `ADMIN_PASSWORD`).
Після входу відкриється дашборд «Моніторинг СУБД PostgreSQL».

Адміністратор із `.env` створюється лише тоді, коли в системі ще немає жодного
користувача. Щоб змінити його пароль пізніше, скористайтеся командою `add-user`
(див. нижче) — редагування `.env` на вже створеного користувача не впливає.

Інтерфейс Prometheus (теж лише після входу): http://localhost:8080/prometheus/

Зупинка (дані зберігаються в томах):

```bash
docker compose down
```

Повне очищення разом з даними:

```bash
docker compose down -v
```

## Керування користувачами

Користувачі зберігаються в SQLite (`/data/auth.db` у томі `auth-data`). Ролі
`Viewer`, `Editor`, `Admin` передаються в Grafana.

* Логін — лише латинські літери, цифри та `. _ -` (він передається в Grafana
  HTTP-заголовком), пароль — щонайменше 8 символів.
* `add-user` для існуючого користувача змінює пароль, а роль — лише якщо її
  вказано явно. Усі попередні сесії цього користувача при цьому завершуються.

```bash
docker compose exec auth python app.py add-user student pass1234 Viewer
```

```bash
docker compose exec auth python app.py list-users
```

```bash
docker compose exec auth python app.py delete-user student
```

Після видалення користувача всі його сесії одразу стають недійсними.

## Дашборд

| Розділ | Що показує | Джерело |
|--------|------------|---------|
| PostgreSQL | статус СУБД, розмір БД, кількість підключень, транзакцій/с, cache hit ratio, відкати, INSERT/UPDATE/DELETE за секунду, кількість рядків у таблицях | Prometheus ← postgres-exporter |
| Генератор навантаження | операцій/с за типом, час виконання p95, помилки і їх частка | Prometheus ← generator |
| Сервер авторизації | успішні, невдалі та заблоковані входи, активні сесії, перевірки доступу | Prometheus ← auth |
| Логи | кількість записів за рівнями, повільні запити PostgreSQL, помилки та попередження | Loki |
| Трейси | останні трейси, трейси з помилками, повільні операції | Tempo |

### Зв'язок логів і трейсів

* **Лог → трейс:** у кожному JSON-лозі генератора є `trace_id`. Розгорніть
  запис логу (у дашборді чи в Explore → Loki) і натисніть посилання **TraceID**.
* **Трейс → логи:** відкрийте трейс, розгорніть span і натисніть
  **Logs for this span** — Grafana покаже логи саме цієї операції.

## Приклади запитів (Explore)

PromQL (Prometheus):

```promql
# Транзакцій за секунду в БД shop
rate(pg_stat_database_xact_commit{datname="shop"}[1m])

# 95-й перцентиль часу виконання операцій генератора
histogram_quantile(0.95, sum by (le, operation) (rate(generator_operation_duration_seconds_bucket[1m])))

# Невдалі спроби входу за 5 хвилин
increase(auth_login_attempts_total{result="failure"}[5m])
```

LogQL (Loki):

```logql
# Усі помилки генератора
{service="generator"} | json | level="ERROR"

# Повільні запити, зафіксовані PostgreSQL
{service="postgres"} |= "duration:"

# Невдалі спроби входу з IP-адресою
{service="auth"} | json | message="Невдала спроба входу"
```

TraceQL (Tempo):

```traceql
{ resource.service.name = "generator" && status = error }
{ resource.service.name = "generator" && duration > 300ms }
{ name = "create_order" }
```

## Сценарії для демонстрації

1. **Невдалий вхід.** Введіть неправильний пароль: на дашборді зросте
   «Спроби входу → failure», у Loki з'явиться запис `Невдала спроба входу`.
   Після 5 невдалих спроб за 5 хвилин вхід для цього логіна з цієї адреси
   блокується («Спроби входу → blocked», HTTP 429).
2. **Помилки запитів.** Операція `invalid_order` порушує FOREIGN KEY. Видно
   одночасно: метрику помилок, запис `ERROR` у логах генератора і PostgreSQL,
   червоний трейс у Tempo з текстом помилки.
3. **Повільні запити.** Операція `slow_report` виконується 0,3–1,2 с. Вона
   потрапляє в «Повільні запити PostgreSQL», «Повільні операції» в Tempo і на
   графік p95.
4. **Відмова СУБД.**
   ```bash
   docker compose stop postgres
   ```
   «Статус СУБД» стає `DOWN`, генератор пише в лог `БД недоступна, повтор…`.
   Після запуску він сам перепідключається:
   ```bash
   docker compose start postgres
   ```
5. **Блокування таблиці.** Інша сесія тримає блокування 20 секунд:
   ```bash
   docker compose exec postgres psql -U shop -d shop -c "BEGIN; LOCK TABLE products; SELECT pg_sleep(20); COMMIT;"
   ```
   Генератор не зависає: запити до `products` через 3 с завершуються помилкою
   `LockNotAvailable` (видно в метриках помилок, логах і трейсах), а решта
   операцій продовжує працювати. Запити моніторингу мають власний таймаут, тож
   метрики PostgreSQL не зникають.

## Безпека

* Ззовні доступний лише шлюз і лише з цього комп'ютера (`127.0.0.1:8080`).
  Grafana довіряє заголовку `X-WEBAUTH-USER`, а шлюз завжди його перезаписує,
  тож підробити заголовок з браузера не вийде.
* Grafana приймає цей заголовок лише з фіксованої адреси шлюзу
  (`GF_AUTH_PROXY_WHITELIST`), тому інші контейнери мережі не можуть звернутися
  до неї напряму від імені користувача. Динамічні адреси Docker видає з окремого
  діапазону (`ip_range`), тож адресу шлюзу не може зайняти інший контейнер.
* Інші способи входу в Grafana (форма, Basic-автентифікація) вимкнені, а
  вбудований адміністратор має випадковий пароль `GRAFANA_ADMIN_PASSWORD`.
* Паролі зберігаються як хеші (`werkzeug.security`), токени сесій — як SHA-256.
* Захист від підбору пароля: 5 невдалих спроб за 5 хвилин блокують вхід для
  логіна (навіть для паралельних запитів), а 30 невдалих спроб з однієї адреси
  з будь-якими логінами — вхід з цієї адреси. Перевірка пароля для неіснуючого
  логіна триває стільки ж, скільки для існуючого, тож за часом відповіді не
  можна дізнатися, які логіни є в системі.
* Невідомі логіни в лог не записуються (`<невідомий>`): туди міг потрапити
  пароль, введений не в те поле.
* Сторінку входу та Prometheus не можна вбудувати в чужий сайт
  (`X-Frame-Options`, `frame-ancestors`) — захист від clickjacking.
* Cookie сесії `HttpOnly`, `SameSite=Lax`, строк дії 8 годин.
* Шлюз перечитує адреси сервісів у DNS Docker кожні 10 с, тому продовжує
  працювати після перестворення контейнерів.
* Мінімальні права: генератор працює з роллю `shop_app` (лише дані таблиць),
  exporter — з роллю `exporter` (лише статистика); власні сервіси (`auth`,
  `generator`) працюють від непривілейованого користувача ОС.
* Alloy читає Docker API через `docker-proxy`, який дозволяє лише читання і
  доступний тільки з окремої внутрішньої мережі: сам `docker.sock` (навіть з
  `:ro`) дав би повний контроль над Docker.
* Усі паролі — лише в `.env` (в git не потрапляє); шаблон — [.env.example](.env.example).
* Версії всіх образів закріплені, тож система збирається однаково при кожному запуску.

## Зберігання даних

Метрики (Prometheus), логи (Loki) і трейси (Tempo) зберігаються в томах Docker
7 днів і переживають `docker compose down`.
